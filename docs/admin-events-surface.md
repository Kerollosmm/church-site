# سطح إدارة الفعاليات والمواعيد (STEP 3)

المرجع التنفيذي لشاشات إدارة الفعاليات المبنية فوق طبقة النطاق/المستودع الحالية
(`src/lib/domain/*`، `src/lib/store/*`، `src/actions/event-actions.ts`). لا اعتماديات جديدة، ولا
متغيرات بيئة مطلوبة، والبناء يعمل بالمحرك الملفي (`.data/church-store.json`) كما يعمل بـ Supabase.

## 1. المسارات

| المسار | النوع | الوظيفة |
| :--- | :--- | :--- |
| `/admin/events` | ديناميكي `ƒ` | فهرس كل الفعاليات وكل السلاسل المتكررة + أزرار الصف + مؤشر آخر تعديل + زر مسح الذاكرة المؤقتة |
| `/admin/events/new` | ديناميكي `ƒ` | إنشاء فعالية (كل حقول النطاق بالعربية والإنجليزية) |
| `/admin/events/[id]/edit` | ديناميكي `ƒ` | تعديل فعالية + نشر/إلغاء نشر/أرشفة/إلغاء بسبب/نسخ/حذف |
| `/admin/events/series/new` | ديناميكي `ƒ` | إنشاء سلسلة متكررة (أسبوعي/شهري) |
| `/admin/events/series/[id]` | ديناميكي `ƒ` | تعديل السلسلة + إدارة الاستثناءات (إلغاء/نقل موعد واحد، والتراجع) |
| `/admin/audit` | ديناميكي `ƒ` | سجل التدقيق: الوقت، الفاعل، الإجراء، الكيان، وملخص «قبل ← بعد» |
| `/admin/media` | ديناميكي `ƒ` | سجل وسائط وصفي (بيانات وصفية + رابط)، مع رفض الحجم الزائد |
| `/admin/login` | **ثابت** `○` | يبقى ثابتاً، ويظهر «سبب» إعادة التوجيه عبر `?reason=` |

كل مسارات الإدارة ديناميكية بحكم `dynamic = "force-dynamic"` في `src/app/admin/(protected)/layout.tsx`
(فحص الجلسة يُعاد في كل طلب)، ولذلك لا حاجة لإضافة أيٍّ منها إلى `EVENT_SURFACE_PATHS`
في `src/lib/store/revalidate.ts` — تلك قائمة **المسارات العامة** المخزَّنة مؤقتاً، والإدارة لا تخزّن.

## 2. الأدوار والقدرات

`src/lib/domain/capabilities.ts` يبني `owner | editor | viewer` فوق `profiles.role` بلا مساس بها:

| الدور | `profiles.role` | يستطيع | لا يستطيع |
| :--- | :--- | :--- | :--- |
| `owner` | `admin` | كل شيء، ومنه الحذف النهائي وإدارة المستخدمين | — |
| `editor` | `secretary` | إنشاء/تعديل/نشر/إلغاء نشر/إلغاء/أرشفة/نسخ، السلاسل، الاستثناءات، التصنيفات، الوسائط، مسح الذاكرة المؤقتة | الحذف النهائي (`event:delete`)، `users:manage` |
| `viewer` | — (لا دور يصل إليه اليوم) | قراءة كل الشاشات | أي كتابة |

- **الواجهة لا تُخفي فقط، بل تُبنى على القدرة**: `resolveAdminCapabilities(role)` على الخادم يعطي
  `AdminCapabilities`، ويُمرَّر إلى مكوّنات العميل، فهي لا ترسم زراً لا يملكه الدور.
- **الأمان في الخادم لا في الواجهة**: كل إجراء في `src/actions/event-actions.ts` يبدأ بـ
  `requireStaff()` ثم `can(role, capability)` ثم zod ثم المستودع، وأي إبطال للكاش يقع بعد النجاح فقط.
- **قيد معروف ومُعلَن**: `viewer` غير قابل للوصول من `profiles.role` حالياً (لا يوجد دور يتحوّل إليه)،
  فالحالة «عرض فقط» مُنفَّذة في الواجهة والخادم وتُختبَر بـ `can("viewer", …)`، لكن الحالة العملية
  للرفض اليوم هي محاولة **محرر** لإجراء **مالك** (مثل الحذف النهائي).

## 3. تسجيل الرفض في سجل التدقيق

أُضيفت قيمة `denied` إلى `audit_action_enum` وإلى `AuditAction` في نطاق الأنواع، ويُسجَّل كل رفض
`authorize()` قبل أن يعيد رسالة الرفض:

```
رفض صلاحية · فعالية · رُفض إجراء «حذف فعالية» — الدور الحالي (محرر (سكرتارية الكنيسة)) لا يملك هذه الصلاحية.
```

- السطر يحمل `before = null` و`after = null`: هو **حدث تدقيقي لا تعديل**، ولا يمكن استخدامه لإعادة كتابة
  تاريخ أي صف.
- التسجيل **بذل وسع** (best effort) ومقصود: إن تعذّرت الكتابة فسُجِّل الخطأ في السجلات، ويبقى الرفض قائماً —
  فلا يستطيع مستخدم غير مخوَّل تحويل كتابة التدقيق إلى مسار خطأ.
- في Supabase تُرقّى قاعدة قائمة بـ `ALTER TYPE audit_action_enum ADD VALUE IF NOT EXISTS 'denied';`
  الموجود في نهاية الملف 8.

## 4. الحالات المُعالَجة (States)

| الحالة | الموضع | الشكل |
| :--- | :--- | :--- |
| لا فعاليات بعد | `/admin/events` | حالة فارغة + دعوة لإنشاء فعالية (أو «دورك للعرض فقط») |
| لا سلاسل بعد | `/admin/events` | حالة فارغة + دعوة لإنشاء سلسلة |
| لا سجلات تدقيق | `/admin/audit` | حالة فارغة، مع تمييز «لا سجلات مطابقة للتصفية» |
| لا ملفات وسائط | `/admin/media` | حالة فارغة + شرح البيانات الوصفية |
| فشل الحفظ/النشر | كل نموذج | شريط نتيجة **قريب من النموذج** برسالة عربية من الإجراء، بلا أي نص خطأ تقني |
| أخطاء الحقول | كل نموذج | رسالة تحت الحقل نفسه + `aria-invalid` + `aria-describedby`، ونقل التركيز إلى أول حقل به خطأ |
| انتهاء الجلسة | `/admin/login?reason=session` | «انتهت جلسة الدخول» + دعوة لتسجيل الدخول (لا يُفقد ما حُفظ) |
| حساب بلا صلاحية دخول | `/admin/login?reason=role` | «هذا الحساب لا يملك صلاحية الدخول» |
| خروج مقصود | `/admin/login?reason=signed-out` | تأكيد الخروج |
| إجراء ممنوع داخل الشاشة | `/admin/events/new`، `/admin/events/[id]/edit`، `/admin/events/series/*` | شاشة `AdminForbiddenNotice` تسمّي القدرة والدور، وتذكّر بأن الرفض يُسجَّل |
| تعذّر قراءة المخزن | كل الشاشات | شريط خطأ صريح بدل قائمة فارغة توهم بأن المحتوى اختفى |

## 5. الوسائط: بيانات وصفية فقط (محدودية مُعلَنة)

- لا يوجد **رفع بايتات** ولا مخزن ملفات: `MediaRecord` يحمل `filename` و`mimeType` و`sizeBytes`
  و`url` و`altAr`/`altEn` و`isPublic` فقط، والشاشة تقول ذلك نصاً.
- تسجيل عنصر = تسجيل بياناته الوصفية ومكان الملف (مسار داخلي أو عنوان). الربط بفعالية اختياري وينفَّذ
  بضبط `imageUrl` للفعالية عبر `updateEventAction` (تحديث حقيقي له سطر تدقيق خاص به).
- الصفحات العامة لا تحمل حقلاً للوسائط؛ الشاشة تشرح ذلك وتذكر الصفحات التي تعرض صوراً.
- **حد الحجم**: `MAX_MEDIA_SIZE_BYTES` (50 ميجابايت) مصدر واحد في `src/lib/validations/event-schemas.ts`،
  يفرضه المخطط على الخادم، وتُبنى رسالة الشاشة منه (`MAX_MEDIA_SIZE_LABEL`) فلا يفترق المُعلَن عن المُنفَّذ.

## 6. لم يُنفَّذ في هذه الخطوة

- محرر مصطلحات التصنيف (الشاشات تقرأ المصطلحات من المخزن كما هي، وتسمح بالوسم بها).
- رفع ملفات الوسائط (بايتات) — لا مخزن ملفات في المشروع.
- تحرير جدول القداسات (`mass_schedules`) — شاشة `/admin/masses` للعرض فقط كما كانت.
- أي مسار عام جديد: `EVENT_SURFACE_PATHS` لم تتغيّر (لا صفحات عامة جديدة).
